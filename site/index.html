Sandboxes for code an AI agent wrote.

cellblock starts a hardened container on demand, streams output while the code runs, moves files in and out, snapshots a workspace, and reaps anything left behind. It is an HTTP service on port 4300 with Python and TypeScript SDKs.

Starting a container is easy. Stopping model-written code is not. A fork bomb must not wedge the sandbox, a timeout must take its grandchildren with it, and SQLite and Docker must agree after a crash.

  1. Exec is killable by group

    Each exec runs in its own session. Its process group id goes to a tmpfs file, so a kill needs only shell builtins. Once a fork bomb has used the pids budget, a forked grep cannot start. That failure showed up in a test, and this design fixes it.

  2. Paths are checked twice

    Paths are normalized on the host, and any .. is rejected outright. The symlink-resolved path is checked again inside the container before any read or write.

  3. Startup reconciles both sides

    Containers with no database row are removed. Rows whose container has gone are marked lost. A warm create costs a database update, and a cold create stays honest about its cost.

What the hardening blocks, and what it does not

Left: each probe from the replay with its observed result. Right: what a container boundary leaves open. Read both before running anything you did not write.

6 blocked, observed in the run

  • Fork bomb. The pids cap stopped it, and the sandbox ran echo afterwards.
  • 400 MiB allocation under a 256 MiB limit. Killed with exit 137. Swap is disabled.
  • Outbound connection with networking off. Network is unreachable.
  • Writes to /usr/local and /etc. Read-only file system.
  • Path traversal through the file API. Rejected with HTTP 400 before reaching the container.
  • Networked sandbox reaching the control plane by name. Connection refused, because host.docker.internal resolves to the sandbox's own loopback.

6 not blocked by a container

  • Kernel exploits. All containers share the host kernel. Untrusted code in production needs a microVM such as Firecracker or Kata, or gVisor.
  • Network egress. network=true is a bridge with full outbound access. There is no allowlist and no DNS policy.
  • The host gateway IP. A networked sandbox can still reach the host by its bridge IP. Only a firewall rule closes that, and this project does not manage one.
  • Side channels and noisy neighbours. CPU caches, timing, and host disk I/O are shared.
  • Processes that leave the group. A setsid double-fork escapes the group kill. It stays within memory and pids limits and dies when the sandbox is deleted.
  • Symlink races. The path check is a time-of-check. The container boundary is the real one.

How it is put together

One control plane, one state file, one backend seam. A Firecracker backend would implement the same interface. Nothing above the seam changes, but it is not built.

Where to look in the code

If you read one thing, read these. Each file holds one of the parts the replay exercises.

  1. backends/docker.py

    Exec is started under setsid, and its group is recorded in tmpfs so a kill is shell builtins only. The container flags (read-only root, cap-drop ALL, pids limit, no swap) live here too.

  2. paths.py

    Rejects .. segments before anything else, then resolves symlinks inside the container.

  3. service.py

    Warm claim, quota, exec records, and reconcile(), which decides what is an orphan and what is lost after a restart.

  4. store.py

    The SQLite schema and the row updates that make a warm create cheap.

Use it

The keyless demo needs only Docker and uv. It starts the server on :4300 with an isolated home, runs the agent example through the SDK, measures create latency, and cleans up.

make install        # uv sync (Python 3.12) + pnpm install (TS SDK)
make demo           # keyless end-to-end run
make test           # 62 Python tests (unit + real-Docker integration)
make test-ts        # 5 TypeScript SDK tests (starts its own server on :4300)

Python

from cellblock_sdk import Sandbox

with Sandbox(memory_mb=256, ttl_seconds=600) as sb:
    print(sb.run_code("print(sum(range(10)))").stdout)   # "45\n"
    sb.exec("pip --version", on_stdout=print)            # streams as it arrives
    sb.files.write("app/main.py", "print('hi')")
    template = sb.snapshot("with-app")                   # save /workspace
with Sandbox(snapshot_id=template["id"]) as sb2:         # restored files are present
    print(sb2.files.read_text("app/main.py"))

TypeScript

import { Sandbox } from "./sdk/ts/src/index.ts";

const sb = await Sandbox.create({ memoryMb: 256 });
await sb.runCode("print('hi')", {
  onStdout: (chunk) => process.stdout.write(chunk),
});
await sb.delete();

The TypeScript SDK is not published to npm. It is imported from the repository for now.

Known limits

  1. No live demo. This page has no backend. Containers share the host kernel, which is not a boundary to trust with strangers' code, so the replay is the only thing to look at.
  2. Single node. No multi-host scheduling and no metrics endpoint.
  3. No TLS, no rate limiting. Put it behind a reverse proxy.
  4. Live model not run. The build had no Anthropic API key, so the demo uses a scripted model.
  5. Node needs an image. run_code in node needs node:22-alpine, which is on the allowlist and tested.
  6. Templates have no quota. Images must be on the allowlist, and templates have no per-key disk quota.
